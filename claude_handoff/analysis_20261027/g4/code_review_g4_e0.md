## 逐项核查

### 1. 往返精确性的检查是否真独立

- **解码端用到的输入**：`_decode` 只把 `data`（varint 长度 + 载荷）、`S`（边上双方共有、已解码的内容）和 `prior` 交给 `run_message(DecIO, …, house, None)`。在解码分支里，`run_message`、`body_w1/w2/w3`、`code_plan`、`code_boxes` 只读 `house.cell`、`house.rcache`、`house.travs`。`house.P32` 只在 `enc` 分支读（第 826–828 行），`T = None`（第 837 行），`describe_w3` 只在编码端调用（第 802–803 行）。位姿由比特流里的 12 个 16-bit 半字重建，高度用协议常数，并且断言等于生成器的所有位姿（第 928 行）。
- **记忆化**：`RenderCache` 以解码出的 float64 位姿字节为键，命中条件是当前世界在缓存条目的已访问集 K 上与缓存逐值相等（第 556–559 行）。`W.observe` 是首次命中光线行进：每条光线经过的体素都记在 out ≥ 0 里，停止体素也在 K 内，所以只要世界在 K 上相同，每条光线的路径和停点就完全相同。这个论证成立，`observe` 的源码我核对过（`mapping_3d_storey_data_v420.py:348–366`，射线出格即死，与 `Traversal` 的假设一致）。位姿解错时键不同，会重新渲染；单测 D 的"解码端 1 cm 位姿"被抓到了 38 处错误。世界解错时 K 上不等，也会重新渲染；单测 B 的"损坏世界"覆盖了这一点。
- **轨迹回放**：`Traversal` 只依赖位姿和公开光线，以位姿字节为键。超出录制末端的部分，只有命中结束的光线才现算，出格结束的光线判死，与 `observe` 一致。单测 B 在损坏世界里核对了回放和直接行进逐块相等。
- **`--no-render-cache` 路径**：`RenderCache(enabled=False)` 每次直接调用 `W.observe`，`travs = None` 时 `event_march` 全部现算，两者是同一套代码去掉缓存，确实等价。实现者的冒烟和单测都没有跑这条路径，所以我做了下面的审计。
- **我的跨进程审计**（`review_e0/audit_indep.py`）：第一阶段在 VAL r1_i0 上按正式路径（缓存和回放都开）跑 3 条线路的 K0、CD-u、CD-c、CAV，共 150 条消息，全部精确，114 个检查全过，渲染命中 883、未命中 8。第二阶段在**新进程**里独立重建 fixture，用只含 `cell` 的存根、无缓存、无回放重新解码每一条消息。结果：**150 条消息 0 个问题**（`AUDIT OK`），共直接渲染 528 次、984 s。逐条核对了以下几项：
  - 每条消息的解码图，与第一阶段（缓存和回放都开）的解码图逐体素相等；
  - 存根上没有出现任何属性访问错误，说明解码器只用了 `cell`；
  - K0 等于生成器自己的地图，CAV 等于 R8 目标；
  - W2 的行进结果与渲染一致；
  - 3 条线路 × 2 档 × 8 个智能体的 CD 最终信念，等于由 fixture 独立算出的 R8 目标。

  结论：解码只依赖比特流和公开常数（光线集、传感器高度、网格、先验表），记忆化和回放没有掩盖任何解码错误，`--no-render-cache` 路径与正式路径等价。这次审计只覆盖 1 房、先验 A、不含 SYNC，但三条线路共用 `send` 和 `_decode`，SYNC 的消息又只是同一套程序在不同 S 上运行，所以足以支撑上面的结论。

### 4. 字节计数是否诚实

- **计入了**：varint 长度字段（`len(data)` 包含它）；8 bit 智能体掩码；每个新智能体 6 个 float32，共 24 B（12 个均匀 16-bit 符号，不做熵编码）；W3 的 kf / kc / lz（均匀分布）、12 bit 盒数、残差表（19 bit 索引 + 三元值 + 停止标志）；区间编码器的终止字节。终止时写出的是落在区间内的最短前缀，尾部的 0 字节省掉，解码端补 0。因为长度字段单独计数，这样做是合法的，单测 A 验证了码长不超过理想码长 + 16 bit。空的 c 档消息记 1 B。
- **没计入、且应当不计**：先验表（只在 TRAIN 半集上拟合，是双方共有的离线模型，预注册允许）；公开光线集；传感器高度；网格 `cell`（会话常数，→ S5）。
- **先验的数据来源**：`panels()` 中 A / B 分别取 `scene_plan('TRAIN', 70)` 的偶数 / 奇数 index，共 3 个分层 × 35 = 105 套 / 半集；VAL / fresh 都来自 `VALIDATION`。v365 按轮廓哈希分 split，TRAIN 和 VALIDATION 按构造不相交。`count_task` 只在 TRAIN 房子上累加计数，评估进程只 `Prior.load`。没有用到 VAL 或 fresh（→ S2 只是把它留成证据）。
