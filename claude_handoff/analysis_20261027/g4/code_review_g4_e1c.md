## 必改项

### M1. fit 产物的来源没有闭环：冒烟 fit.json 能被正式 eval 当成完整拟合使用

- **位置**：
  - `g4_calib_stalk.py:403-404`：`complete` 用的是运行时的 `min_fit_houses`。
  - `:710`：smoke 时 `min_fit_houses = 1`。
  - `:711-712`：fit 阶段跳过已存在的 fit_jobs，不核对其 script sha 与种子。
  - `:348-365`：`fit_aggregate` 也不核对。
  - `:527-531`：只在给了 `fit_path` 时才查 `complete`。
  - `:727-729`：eval 不查 fit 内容。
  - `:747`：aggregate 阶段 `--fit` 可省。
- **问题**：
  - 冒烟的 `e1c_smoke/fit.json` 写的是 `complete: true`，但每个半集只有 1 房，噪声种子是 7。正式 eval 若误指向它，判决不会报 INCOMPLETE。
  - `aggregate` 阶段不带 `--fit` 时，fit 检查整段被跳过。
  - 也没有核对 fit.json 的 sha 是否等于任务文件里记录的 `fit_sha256`。
  - 改脚本后若复用旧的 `--out`，旧 fit_jobs 会被静默沿用。
- **改法**：
  1. fit.json 记录 `smoke`、`train_per_stratum`，以及每半集的 `world_ids`。
  2. 非 smoke 的 eval 拒绝满足下列任一条件的 fit.json：`smoke=True`；任一半集 `n_houses < 12`；`seeds ∩ {1, 2, 7} ≠ ∅`；`failed` 非空；半集 world_id 相交。阈值 12 直接写在判决侧，不读 fit.json 里的 complete。
  3. 非 smoke 的 aggregate / verdict 必须拿到 fit.json（显式 `--fit`，或从 eval 输出目录的 run 记录取），并重复第 2 条检查。另外核对：`file_sha256(fit) == 任务文件里唯一的 fit_sha256`；`fit['script_sha256'] ==` eval 任务的 script sha。任一不满足 → INCOMPLETE。
  4. fit 阶段遇到已有的 fit_jobs，若 `script_sha256` 或 `seeds` 不同，就拒绝（照 eval 的 `:740`）；`fit_aggregate` 断言所有 fit_jobs 的 script sha 与种子一致。

### M2. 缺 fresh 面板时，"fresh 符号与 VAL 相反时降为 ambiguous" 被绕开

- **位置**：`g4_calib_stalk.py:584-598`（只检查 VAL 的完整性）、`:620-628`、`:638-641`。
- **问题**：
  - fresh 只在存在时才参与降级。探针 `lever_no_fresh` 在没有 fresh 时直接判 LEVER。

### 6. clean 档半集 B 家具 .998（不是 1）

- **原因**：B6_B 在 clean 上只有虚警，没有漏检：两个冒烟房分别是 fp 20 / 33，tp 4420 / 7527，fn 0，空闲召回 .99979 / .99986。
  - 拟合出的 cam_nf 表不单调：c(−8) = +23 单位（+1.15 logit）、c(−16) = +6。也就是说，在 cam_nf 里，"恰好一次未命中、没有击中"更常出现在占据体素上：测距噪声与位姿噪声会让个别束穿过表面体素；真空闲的体素则通常被多束扫过，被截到 −40 附近。
  - 半集 B 的 θ = 41 < 2 × 23。于是 clean 世界里，一个空闲体素只要被两台机器各一束擦过（每台 L = −8），就被判占据。
  - 半集 A 的 θ = 85，需要 4 台这样的机器，所以冒烟里 A 是 1.000。
  - K0 不受影响：−36 + 23 < 5。
- **含义**：
  - 是的，这张表在干净证据上会犯错。这是设计使然：它是 cam_nf 传感器的似然，放到 clean 证据上属于分布外。
  - .99 的护栏只能防严重退化，冒烟离护栏还有约 10 倍余量，不检验精确性。
  - 正式拟合有 15 房，θ 会更稳；但如果 θ 落到 23 以下，单机 L = −8 就会成为虚警，clean 档可能跌破 .99。那会挡住 LEVER，方向保守，不偏向通过。
- **对"后果"一节的影响**：若判杠杆，"B6 成为证据 stalk 的默认做法"必须写成**每种传感器一张表**。D8-41 (a) 的"clean 与 S0 逐体素精确"在 cam_nf 表下不再成立；clean 传感器的表应退化为恒等表，也就是 B4。
- **建议**：summary 增报 clean 档中 B6 与 B4 判决不同的体素数，并按 k 拆分。

### 7. 按 k 的校准斜率（VAL 冒烟，B6：k = 1 时 .72 / .78，k ≥ 5 时 .51 / .51）

- **斜率随 k 下降**，复现了 R-A 探针里 Σc 在多机时过度自信的结论（RA 是 1.04 → .64）：给定真值后，各机证据仍然正相关，因为误差来自共享的几何，比如同一个薄面、地板顶面落在体素边界上。
- **常数缩放被 t 吸收**，对阈值判决无影响；只有"最优阈值随 k 变"才会改变判决。
  - 冒烟里截距随 k 从 −0.3 变到 −3.6，变化很大。所以单靠 w(k) 缩放、共用一个偏置，参数化偏弱。
  - 冒烟的 W 行增益是 +0.2 / +0.7 pp，落在 R-A 预测的 0 到 +1.5 pp 内。
  - 这确实提示读出端需要依赖 k，而且更可能需要按 k 的偏置或阈值，不只是缩放。这是 E3-R（读出端学习、输入含 k）的天然入口。在 E1c 里保持只报告即可，不要因此改判据。
- **k = 1 斜率 < 1**（RA 是 1.04）：冒烟每半集只有 1 房，表过拟合，极端格如 c(−40) = −113 / −132 单位；另外 c 是跨所有 k 合并拟合的，而 k = 1 的体素多在视野外围、远距离，噪声随距离增大。所以校准只看正式拟合。
- **E3 的提醒**：RA §4 的 E3 草案把"w ≡ 1 时 k ≥ 3 的斜率 < .5"设为重复计数的判据，B6 冒烟已到 .51–.53，正式读数要留意。

### 8. 字节

- **计数是诚实的**：

### 9. 资源与并行安全

- **本机**：32 逻辑核（i9-13900HX），64 GB 内存，当前空闲 23 GB，约 11 个 python 进程（E4 用 8 个 worker，另有 E0 审计）。
- **内存**：E1c 每个 worker 峰值约 0.86 GB，4 个约 3.5 GB，安全。
- **CPU**：E4 + E1c 约 12–13 个忙线程，低于 32；但会排到 E 核上，预计 fit 30–40 min、eval 80–120 min，比实现者估计的略长。
- **文件**：
  - 写入的目录（`e1c/`、`%TEMP%/g4_e1c_cache`）与 E4 不重叠；E1 jobs 两边都只读。
  - 缓存在仓库外（`:709` 的断言只对非 smoke 生效），正式 30 房 × 2 种子约 45 MB。
  - eval 任务 JSON 只含计分行与稀疏校准直方图，没有体素地图或 HouseExpo 几何，符合"公开仓库不放原始数据"的约束。
- **建议**：worker 数保持 ≤ 4；如果 E0 正式运行同时启动，eval 墙钟时间会再拉长。
