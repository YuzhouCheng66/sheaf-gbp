## Findings

### 1. Diff discipline (priority 1): PASS, with one vacuous "strict" load (MAJOR)

- The v348 -> v350 diff contains nothing but the edge selection, the dynamic data loader and CLI/meta plumbing (table row 1). `evaluate` (L527-572) is identical to v347/v348 except that `positions_m` is passed to the rollout (L548); with `EDGE_SELECT_M = 0`, `edge_selection` returns ones (L118-119) and the `* sel` is an exact multiplication by 1.0 in FP64, verified `torch.equal` against the rollout without positions. The v347 max rollout itself did not change between v347, v348 and v350 (`wire_q = forest.quantize` when `--wire sealed`, L257; `latent_quantize` levels = 127 when `--mu-bits 8`, L241), and `test_v347_max.py` passes against the v350 module. Therefore `evaluate(val)` in a v350 run is numerically comparable to v347's `final-val.json` (same `scene_plan('VALIDATION')` specs, same `select_forest` edges, same rollout, same `node_metrics`, same stratum aggregation).
- `--epochs 0`: `range(1, 1)` is empty (L580), `total_updates = 0` is guarded by `max(1, .)` in the scheduler (L512), `final.pt` is written (L633) and `evaluate(val)` / `evaluate(fresh)` run on the loaded weights (L634-643) through the same `model.source -> rollout -> predict` path as training (L532, L548, L552 vs L588-589, L592); `EDGE_SELECT_M` is a module global set at L429 and read inside `edge_selection` at L118, so the selection is applied in both panels (448 calls counted in the smoke run). `model.eval()` is never called in this path, which is harmless because the model has no mode-dependent layers.
- MAJOR (M1): the warm start is not strict. L502 keeps only same-name same-shape tensors, L504 calls `load_state_dict({**own_state, **loaded}, strict=True)`, which can never fail because the dict is always complete; only `arm` is asserted (L507). A checkpoint whose `readout_mode`, `precision_mode` or `mu_bits` differ from the CLI loads silently with the first decoder layer (or more) at fresh init (demonstrated: 39/40, `fresh ['decoder.pre.0.weight']`, run continues). For a zero-shot sweep this would produce plausible-looking but meaningless numbers that could be mistaken for a "bad R". The planned commands are consistent with the v347 run (`--readout posterior_only`, owned, 8-bit sealed wire; see `chain_v347_sum.sh`), so this is a hygiene gap, not a wrong result today. Patch A below makes a partial load fatal unless explicitly allowed (the H256 continuation legitimately adds new `decoder.trunk.blocks.4.*` tensors and needs the flag).

### 2. Edge selection restriction map (priority 2): PASS on orientation and semantics; two notes

- Orientation: block centres `c = (arange(8)+.5)*2.5` (L120), `cy, cx = meshgrid(c, c, 'ij')` (L121) so `cy` varies along dim 0 (rows) and `cx` along dim 1 (cols); `mid = (x, y)` from `positions_m` (L122) which the sealed generator defines as `pose=(x,y); raster=[y,x]` (v293 L69, L163, L165: `positions_m = trajectory[-1]`); `dist` uses `cx - mid[0]`, `cy - mid[1]` (L123); row-major flatten (L124). `PatchTrunk` unfolds `[N,5,8(rows),8(cols),p,p]` and reshapes row-major (L103-104); `OwnedHead.observed` uses `avg_pool2d(...).flatten(1)` (L154); `OwnedDecoder` reshapes `(b,1,8,8)` (L195). All four agree (block 14 probe in the table). No transposition.
- Semantics: multiplying the wire-quantised message by the 0/1 selection (L287-288 sum, L356-357 max) is a valid partial-identity restriction map for both fusions. Sum: the receiver's belief is `p_own + sum(msg_p)` (L276-277), so a zeroed coordinate contributes exactly nothing and the receiver keeps its own factor (verified to equality). On a forest the per-coordinate subgraph induced by the edges whose stalk contains that coordinate is a sub-forest, so sum-product stays exact per coordinate with no double counting. Max: the belief and the relay use `select` with the own factor first (L340-342, L353-355), own precision is at least the prior > 0, so a zero-precision message never wins (verified). Relay follows the intersection of stalks along the path (verified: no new information crosses an edge whose stalk lacks the coordinate). The selection is symmetric and computed from the two endpoint positions only (L122), which are declared public inputs (README section 3: poses available; section 4.2: v329-v340 restrictions were already generated from "public endpoint positions"; bank L87-107 forest scheduling is "offline public schedule"). The dynamic/edge paths never let a node read another node's raw map: `model.source(sc['own_t'])` encodes each agent independently (PatchTrunk per agent, L98-107; OwnedHead per block, L150-160); other agents' maps enter only `forest_targets` (targets, L461, L476) and `node_metrics` (scoring, L553).
- NOTE (N1): in the sum path the profile-4 block exponent is computed over all 64 cavity coordinates before the selection is applied (forest L185-186 vs trainer L287-288), so dropped coordinates with large |eta/sqrt(p)| can coarsen the kept ones. A real sender would compute the exponent over the stalk only; the current code is slightly pessimistic for `--fusion sum --edge-select R`. The max path quantises once at the source over all 64 coordinates (L336) and is unaffected by this point. The planned sweep uses max.
- NOTE (N2): targets are unchanged by the restriction (`forest_targets` = union of everything within k forest hops, bank L118-122). Under selection, a block of source s reaches node j only if it lies within R of the midpoint of every edge on the path, so part of the F1 drop versus R is information the protocol does not deliver by design, not decoder failure. Report alongside the sweep the fraction of target-known cells that lie in blocks not deliverable under R (computable from public geometry), or a "restriction-reachable" target, so that the quality-versus-bytes curve is interpretable. `edge_select_bytes.py` already reports the sender-side cut (0 % at R >= 12, 3 % at 8, 17 % at 6).
- NOTE (N3): when `EDGE_SELECT_M > 0` but `positions_m is None`, both rollouts silently fall back to identity (L287, L356). All trainer call sites pass positions; `eval_dynamic_v349.py` L144 does not (it runs at R = 0). An `assert positions_m is not None` when `EDGE_SELECT_M > 0` would prevent a silent identity evaluation in a future combination.
- NOTE (N4): `edge_selection` is evaluated per directed message per round with two host-to-device copies (L122): 240 calls per N=16 rollout. 17 ms on CPU; on the GPU perhaps tens of ms per rollout, i.e. seconds per panel, negligible for the planned zero-shot sweep. For the dynamic fine-tune at R=0 the call is a single `torch.ones`. Precomputing one `[2E,64]` selection tensor per scene is an easy speed-up if selection is ever trained.
- NOTE (N5): `edge_select_bytes.py` reports a coordinate fraction, not bytes. To state packet bytes: the receiver can recompute the stalk from the public endpoint positions (no mask needed, but the position exchange, 2 x 2 floats per directed edge per step, must be billed once), payload = 2 B x kept coordinates (plus the per-source exponent issue in finding 4, M4), header as in the sealed 172 B packet (148 B codec frame + 24 B session binding, forest L4, L243). At R=6 that is roughly 44 + 2*17 = 78 B versus 172 B, i.e. about 2.2x, not 3.7x, if the sealed header is kept.

By construction poses are accepted only inside a room rectangle with 0.45 m margin, inside the corridor with 0.3 m margin, or inside the door rectangle with 0.05 m margin (L54-59, L61-64); the door case is the only tight one (door rectangles are the 0.3 m slab span, v293 L63-64) and is safe because the agent's y is within 0.3 m of the door centre when it heads for the corridor (L51), which keeps the cell centre inside the 0.8 m opening at H128 (margin 0.022 m); at H256/512 the margin is larger.
- Determinism: `rng = default_rng(sha256(world_id + ':dyn349:' + agents))` (L18-19, L35); `world_spec` is deterministic from (split, index, rooms) (v293 L53-54). Regeneration is bit-identical.

Nothing in the three files can generate TEST. `eval_dynamic_v349.py` exposes `--split` (L22) without its own guard but inherits this one. `load_dynamic` takes the split from the v306 plan specs (TRAIN only, L451).
- Cumulative maps: `current = np.maximum(current, observed)` (L85) is exactly the v293 multi-pose merge (`private = np.maximum(private, observed)`, v293 L134). With this sensor a conflict (free once, wall later) cannot occur: `raycast_observe` writes the truth value of each traversed cell (v121 L193) and a beam dies at its first occupied cell (L195), so a wall cell is only ever written as 1 and a free cell as 0; the only transitions are -1 -> 0 and -1 -> 1. Verified: 0 non-monotone slices, and `forest_targets`' conflict check (bank L116) never fired. So the maps are monotone in information, as a memory benchmark requires.
- Sensor: same `make_rays(SENSOR_RANGE/cell, 256)` and 5 m cell-centre mask as v293 L126-133 (dyn L72, L82-84). t=0 map = observation from the third v293 pose (`start[-1]`, L37) and is a subset of the static 3-pose map (24/24 checked).

- Resource/time: 0.08 s per spec on this 2-core CPU including the five targets per slice; the 592-spec TRAIN set generates in about 1 min. `load_dynamic` (trainer L466-480) builds `inp` with exactly the five keys `forest_targets` requires (bank L112) and uses the same `select_forest` arguments as `forest_targets`, so rollout edges == target edges on every slice (same invariant as the static loader, L461-462).

### 4. `eval_dynamic_v349.py` (priority 4): correct protocol arithmetic; two MAJOR issues for the claims it supports

- Same codes to both protocols: PASS. `mu, q, mask = model.source(own)` once per step (L93); CRDT uses `forest.quantize(p_own, e_own)` (L95), the same profile-4 wire the sum rollout applies internally (trainer L257, L311). Asymmetry to disclose: the CRDT node's own factor is the quantised one (`join([mem, pw])`, L102) while the stateless-sum belief keeps the unquantised own factor (v295 convention); this handicaps CRDT slightly at own coordinates (precision rounding up to 9.6 %, eta up to 3 code steps), never the reverse.
- CRDT target legitimacy: PASS. `V[i,i] = t` (L101); the forwarded version vector `vv` is the join of the sender's `V[i]` and the incoming vectors except the receiver's (L111-114); the receiver updates `V[j]` only from received packets (L131-132). The target (L137-141) uses ground-truth maps for scoring only. Own map is included (V[i,i]) so `node_metrics`' subset check (metrics L61-62) holds.
- Stateless-sum target: PASS. `forest_targets(inputs_t, R)` on the current maps, positions and adjacency (L146-147) = forest-reachable current union; same `select_forest(.., 8.)` as the rollout (L96).
- MAJOR (M2) - missing control for the "memory" claim: the only stateless protocol is Gaussian SUM (L38, L144), while the checkpoint under test was trained with MAX fusion. The report (D3-2) itself documents that a max-trained decoder collapses under sum (t5 .65/.54) and a sum-trained one under crdt. The comparison "crdt beats stateless sum" therefore confounds (a) memory versus no memory with (b) max versus sum fusion under a decoder adapted to one of them. The pre-registered gate (own K0 at t=5 and CRDT F1 at t=5 versus the zero-shot of the same checkpoint) is within-protocol and unaffected, but any statement that memory helps needs a stateless MAX protocol on the current forest with the same codes: `rollout_max = trainer.make_rollout(forest, latent_quantize, 'max')`, `feats_max, _ = rollout_max(mu, q, mask, graph, rounds=R, stages=(0, R))`, scored against `target_sum` (the forest-reachable current union is the right target for any stateless protocol). The max rollout is a drop-in (same signature, L323).
- MAJOR (M3) - byte comparison is not like-for-like: CRDT is billed with diff coding and silence (`(8 + 8 + 2*changed + n) if changed else 0`, L124) while the sum protocol is billed full 172 B packets on every directed edge every round (`2*len(graph)*R*PACKET`, L150). On a forest the sum messages converge after at most diameter rounds and are then repeated verbatim, and across steps most coordinates are unchanged, so the same diff/silence rule applied to the sum packets changes the picture by a large factor: in the instrumented replica (untrained model) crdt_diff/sum_full = .059 but crdt_diff/sum_diff = .29. The headline "11.5 % of the bytes" in D3-2 compares a diff-coded protocol with a non-diff-coded one. Bill both with the same rule (keep `sum_full` as the sealed reference and add `sum_diff`), and report `crdt_full / sum_full` (already computed, L170, > 1 by construction since both send the same packet count) next to it.
- MINOR (M4) - undercounts inside the CRDT diff formula (L124): (i) version information is delivered for free: when `changed == 0` the packet is billed 0 B, yet the receiver still applies `V[j] = max(V[j], msg[b][2])` (L132); 1,079 of 3,205 silent packets in the replica carried a changed version vector; a real protocol must send at least header + N bytes in that case (billing it raised crdt_diff by 68 % in the replica). (ii) header: 8 B versus the 44 B of overhead inside the sealed 172 B packet that the sum protocol pays (148 B codec frame + 16 B nonce + 8 B weight, forest L4, L226-243); use the same header assumption on both sides or strip the binding from both. (iii) "2 bytes per changed coordinate" assumes one block exponent per packet (forest L185-192), but a joined packet can mix coordinates quantised at different sources with different exponents (the max/CRDT relay forwards source codebook values, trainer L334-336); such coordinates need their exponent (about 5 bits) or a per-source exponent table plus a source index. No mixed-exponent packet occurred in the untrained replica, so the practical cost may be small, but the assumption must be stated; the same caveat applies to the v347 172 B max packets. (iv) the 64-bit change mask is present (second `8`); the N version bytes are correct for T <= 255.
- MINOR (M5) - the CRDT is "max precision ever heard", not "latest version of each source": the join keeps an older factor of a source whenever its quantised precision is higher than the newer one's (version is only a tie-break, L54-58, acknowledged at L103), while the TARGET uses the latest known version of every source (L140-141) and the docstring says the node keeps "the latest version it knows of every source". With cumulative maps the stale factor encodes a subset, so this only lowers the CRDT score (conservative, no leak), but it is a real protocol weakness with a learned, non-monotone precision head: 57 % of held coordinates were stale in the untrained replica; for the trained checkpoint the effect is bounded by the gap between `own_wall_f1` under crdt and own K0 (report: .823 vs .833 at t=5 for s342101). Per-source version dominance (a newer version of the same source always replaces the older one) needs a source id per coordinate on the wire (4 bits for N <= 16) and would make the memory match the target definition. Either fix the protocol or change the docstring and the target to "most precise factor heard".
- MINOR (M6) - `decode()` feeds `cat((feats, feats))` (L71), which is correct only for `posterior_only` readouts (OwnedDecoder uses `features[:, 128:]`, trainer L193-195). For an `anchored` checkpoint the own half would be the posterior. Add `assert trainer.READOUT_MODE == 'posterior_only'`. Also `MU_BITS/Q_BITS/WIRE` are not restored from `meta` (L35-36), so a v348 k-bit checkpoint would be evaluated with the 8-bit alphabet silently; irrelevant for v347 but worth a one-line restore.
- NOTE (N6): the sender's outgoing message is `join(mem[i], incoming except j)` (L108-110) but `mem[i]` already absorbed j's previous message at the receive step (L130), so the cavity exclusion is ineffective and i echoes j's information back. Harmless for a join-semilattice (idempotent) and it only inflates CRDT bytes, never deflates them.
- NOTE (N7): `codes = (pc.cpu().numpy().round(12), ...)` per directed edge per round forces a device sync (L117); fine for evaluation.

### 5. Gate soundness and warm start (priority 5)

- Comparability: `evaluate(val)` in the dynamic run is the same code, specs, forest and metric as v347's `final-val.json` (finding 1), so the "static VALIDATION K0/R8 not worse than -1 pp" clause is well defined. State explicitly that it is measured on `final.pt` (final weights, like v347) and not on `best.pt` (selected on the static val R8 F1, L620-623).
- Leakage via `--init-from`: the v347 `final.pt` is the last-epoch weight set, not the VALIDATION-selected `best.pt`, but the v347 budget (36 epochs), fusion choice and readout were fixed after inspecting VALIDATION, and the dynamic gate is also measured on VALIDATION episodes (indices 0-7 = the same 8 worlds as the static panel). This is consistent with the README's status of VALIDATION as a development panel (section 5.1) but it means the gate is a development-panel result. There is no never-selected dynamic panel yet: run `eval_dynamic_v349.py --indices 8-15` once, on the final weights only, as the dynamic counterpart of `fresh` (the generator accepts any index < 1e9; `checked_spec` is not on this path).
- Zero-shot reference: the eval's numbers do not depend on which trainer file is passed (v347 and v350 `rollout_sum` are the sealed path; the CRDT loop lives in the evaluator), so the existing `zeroshot-v347max-s*.json` are valid references for "+3 pp".
- What the fine-tune changes relative to v347: cumulative single-trajectory maps (known fraction 3.6-11 % versus 5-6 % static), per-step forests, and supervision that is stateless per slice (forest-reachable current union) while the gate protocol is the CRDT memory (mixed versions). That mismatch is already present in the zero-shot and is acceptable for the pre-registered gate, but say so.
- Optimizer/RNG: only weights are inherited (L499-504); AdamW state, scheduler (200-update warmup then cosine to 5 % over `6 x 3552 = 21,312` updates, L510-512) and the data-order RNG restart. README section 10 asks that "inherit weights / Adam / RNG / cursor" be declared in the protocol; record "weights only".
- Update count and time: 21,312 updates = v347's 36 x 592. v347 max arms ran 56 s per 592 updates when co-scheduled (`chain_v347_sum.sh` header), i.e. about 34 min of training plus 3 static validations, finals and about 1-2 min of data generation: comfortably inside a 7200 s lease if run alone, but the planned command carries no `--deadline-epoch/--deadline-total` (defaults 1e18, L409-410), so the lease is not enforced by the script. - MAJOR (M7) - device memory: the trainer caches `tgt` (int8) and `dt` (float32, five hops) on the device for every training item (L491-495).
